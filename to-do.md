## Фаза 5. Планировщик (§5, §7) ✅ реализовано (планировщик отработал вживую)

In-process cron раз в минуту (`services/scheduler.ts`): бот и так крутится
постоянно, так что это `setInterval`, не внешняя джоба — один индексированный
запрос на тик, ресурсов не ест.

- [x] **Джоба раз в минуту**: дешёвый предикат `isReminderDue` (юнит-тесты) —
      сегодня ещё не запускали И локальное время ≥ `review_time` — проверяется
      ПЕРВЫМ, без БД; `countWords` зовём только когда напоминание реально пора (и
      колода непуста), чтобы не гонять COUNT каждую минуту впустую. **`≥`, а не `==`**
      — self-healing: если бот лежал в момент времени, ближайший тик после подъёма
      всё равно выстрелит (стамп «сегодня» держит это до одного раза в день). Времена
      — строки `HH:MM` (`timeInTz`), сравнение лексикографическое.
- [x] **Доставка — уведомление + кнопка** «🔔 Регулярное повторение: N слов»
      (`N = min(review_count, колода)`, плюрализация ru) + `[Начать]` (callback
      `review:start`). Тап идёт через обычный middleware → тот же `startReview`, что
      и `/repeat`, и **редактирует то самое сообщение** в первую карточку (передаём
      `reuseMessageId`). Так планировщику не нужно инъектировать сессию извне.
- [x] **Никакого due-гейта:** что ревьюить — целиком дело `startReview` (N с
      наименьшим `next_review`), 1-в-1 с ручным запуском. Планировщик решает только
      «пора ли по времени».
- [x] **Идемпотентность** через `users.last_reviewed_on` (date, в TZ юзера):
      планировщик ставит её ПОСЛЕ успешной отправки (провал стампа → перешлём через
      минуту, это лучше, чем стамп-до-отправки и молчаливый пропуск дня); `startReview`
      ставит её на любом старте → **ручной `/repeat` пропускает сегодняшний плановый**.
- [x] Изоляция per-user (try/catch на каждого) + re-entrancy guard (медленный тик не
      наложится на следующий) + graceful stop (`task.stop()` в shutdown — уже было).
- [ ] **Rate-limit ~1 msg/сек на чат / `429`+`retry_after`** — отложено до мультиюзера:
      при одном whitelist-юзере и ≤1 сообщении в день 429 недостижим, троттлер был бы
      мёртвым кодом. Структура отправки уже безопасна (последовательно, per-user
      try/catch). Включить `@grammyjs/auto-retry` при снятии whitelist (Бэклог).

## Фаза 6. Настройки (§9) ✅ реализовано (ждёт живой проверки)

Меню — **одно редактируемое сообщение, кнопочное, БЕЗ FSM-режима и стейта**
(`features/settings.ts`): каждый экран (главный / редактор счётчика / выбор часа) —
чистая функция от строки `settings` + размера колоды, под-экран закодирован в
callback-данных (`set:*`), id сообщения берётся из callback'а. Поэтому новый режим в
FSM не нужен, и меню **переживает рестарт** (терять в памяти нечего). Свободный ввод
не используется — значит и чистить нечего.

- [x] **`review_count`** (потолок = размер колоды, §9): показываем/редактируем
      ЭФФЕКТИВНОЕ значение `reviewSessionSize(stored, deck)` — ровно то число, что
      запустит сессия, так экран не разойдётся с планировщиком/`startReview`. Степпер
      `±1/±5` шагает от эффективного значения (no-op на потолке НЕ перезаписывает
      хранимое — дефолт переживает рост колоды).
- [x] **`review_time`** — только часы (сетка 6×4, 00–23), минуты пришпилены к `:00`;
      планировщик технически поддержал бы минуты (выбор гранулярности — за UI).
- [x] **`test_count`** — без привязки к колоде (пул теста — подвижное not-due
      подмножество), степпер `±1/±5` в диапазоне `[1, TEST_COUNT_MAX=50]`.
- [x] Валидация = клэмпинг в чистом `lib/settings` (`reviewCountMax`,
      `effectiveTestCount`, `clampInt`) → значение валидно по построению; `review_count
      >= 1`, `test_count >= 1` гарантированы (плюс защитный `max(1, …)` в
      `reviewSessionSize` остаётся для рантайма). Юнит-тесты на клэмпы и рендеры.
- [x] БД: `getSettingsByChatId` (read, включая `review_time`) + `updateSettings`
      (partial-патч; `timezone` намеренно НЕ пишется — env-seeded) в `db/users.ts`.
- [x] Команду `/settings` чистим из чата; `[Закрыть]` удаляет панель (§UX).
- [ ] (Будущее) 4-й пункт — выбор таймзоны (known_issues №6); env `OWNER_TZ` станет seed-дефолтом.
