# Design Doc — Telegram-бот для изучения английских слов

## 1. Обзор

Персональный (пока) Telegram-бот для пополнения и тренировки англо-русского
словаря по принципу интервального повторения (SRS). Три активности:

- **Добавление** слов (русских или английских) — режим по умолчанию.
- **Повторение** — активная тренировка: показываем русское слово, **печатаешь
  английский перевод**; по расписанию или командой `/repeat`.

Изучение всегда в направлении **RU→EN** (показываем русское, ждём/проверяем
английское), независимо от того, на каком языке слово добавили. Раньше было две
тренировки — пассивное узнавание («повторение») и активная печать («тест»); слиты в
одну, активную: пассивное чтение не закрепляет, печать (active recall) закрепляет.

## 2. Стек и ключевые решения

- **Node.js + PostgreSQL.**
- **Telegram-библиотека: grammY** — TS-first; плагины *conversations* (пошаговый
  флоу добавления слова) и *sessions* (FSM-состояние пользователя).
- **Перевод: Yandex Dictionary API** — авторитетный курируемый словарь (смыслы,
  часть речи, синонимы). НЕ LLM.
- **Генерация примера и фоллбэк для редких слов: LLM через Vercel AI SDK**
  (`ai` + `@ai-sdk/groq`). Провайдер переключается через env `LLM_PROVIDER`
  (сейчас **Groq**, модель `openai/gpt-oss-120b` — бесплатно/без карты, есть
  structured output). Structured JSON — `generateObject` + zod-схема. Добавить
  openai/anthropic/mistral = ветка в фабрике модели (`services/llm/model.ts`) + ключ.
- Источник перевода и LLM — **за интерфейсами** (`LlmProvider`/`DictionaryProvider`),
  чтобы менять провайдера без переписывания.
- **Планировщик: собственный (cron).** Нативной отправки «в 9:00» у Telegram нет
  — бот сам шлёт `sendMessage`. Бот не может написать первым тому, кто не нажал
  Start → сохраняем `chat_id` на `/start`. Учитываем лимит ~1 сообщение/сек на чат.
- **Мультитенантность: схема с первого дня** (`user_id` во всех таблицах, все
  запросы фильтруют по нему), **но фичи мультиюзера не строим** — пока whitelist
  своего `chat_id`, без онбординга. Появится второй юзер — снять whitelist +
  добавить онбординг, без миграций.
- **Провижининг на `/start`:** идемпотентно создаём строку `users` + дефолтные
  `settings` (на них висят FK у `words`). `OWNER_CHAT_ID` валидируется как целое
  на старте — иначе whitelist молча заблокирует всех, включая владельца.
- **Надёжность процесса:** `bot.catch` для контролируемого лога ошибок (стабы
  кидают `not implemented`), `pool.on('error')` на пуле PG, graceful shutdown по
  SIGINT/SIGTERM (`bot.stop()` + `pool.end()` + остановка cron).
- **Прод-деплой: Docker-образ + long polling (решено).** Образ собирается в GitHub
  CI → GHCR (private) → Coolify на VPS тянет его и перезапускает по деплой-вебхуку
  (конвенции — `infra/deploy-playbook.md`). **Telegram-вебхук НЕ используем**: при
  одном пользователе long polling даёт нулевую входящую поверхность — боту не нужны
  ни домен, ни DNS, ни открытый порт вообще; пересмотреть при мультиюзере. Сборка —
  tsup-бандл СВОЕГО кода (ESM с extensionless-импортами не запускается из голого
  tsc-emit), зависимости — внешние, в образе как pruned `node_modules` (полный бандл
  ломал рантайм-инварианты deps; см. tsup.config.ts). **Миграции применяются на
  старте контейнера** (программный мигратор drizzle-orm, `src/migrate.ts`,
  fail-fast в entrypoint) — бот не стартует на неприменённой схеме. Liveness —
  `/healthz` на localhost (`src/health.ts`) под Docker HEALTHCHECK: 200 только
  когда поллинг реально запущен. Non-root (`node`), `exec` в entrypoint → PID 1 =
  node, SIGTERM доходит до graceful shutdown.

## 3. Принцип использования LLM

> **LLM — только там, где её ошибка дёшева и заметна пользователю. Авторитетный
> API — там, где ошибка молчаливая и вредная.**

- **Перевод** — молчаливый (учишь слово, не можешь проверить) + вредный
  (зазубришь неверное) → **словарь, не LLM**.
- **Пример** — виден и проверяем (зная перевод) + низкий вред → **LLM**.
- **Грейдинг повторения** — крутится без присмотра → **детерминированный, без LLM**.

## 4. Флоу: добавление слова

Режим по умолчанию (IDLE). Пользователь присылает слово.

1. **Определение языка по алфавиту:** кириллица → русское, латиница →
   английское. Без LLM/детектора.
2. **Перевод через Yandex Dictionary** в нужном направлении (`ru-en` / `en-ru`).
   **Двухстадийный поиск:** сначала по точной введённой форме (без флагов) — для
   словарных форм (дом, крыло) чистые списки смыслов; если пусто — повтор с флагом
   `MORPHO` (поиск по лемме), который вытаскивает словоформы (продолжаем → продолжать
   → continue, идём → идти → go) перед фоллбэком на LLM. MORPHO только как фоллбэк:
   на точных совпадениях он подмешивает чужие леммы (крыло → «крыть»=cover, дом →
   нареч. «дома»=at home).
   Смысл = один `tr` (НЕ `def`: те группируют по части речи). Все `tr` со всех
   `def` сводим в плоский список, отсекаем низкорелевантный хвост по `tr.fr`
   (страховка: если все низкие — оставляем все). Каждый смысл = ОДИН перевод
   (`tr.text`); синонимы `tr.syn` НЕ берём — у карточки один ответ.
   - **один смысл → сохраняем сразу;**
   - **несколько смыслов → выбор:** варианты с русским глоссом (`tr.mean`)
     перечисляем в ТЕКСТЕ сообщения, кнопки — номера (длинный текст кнопки Telegram
     режет).
   - **Карточка всегда RU→EN.** По направлению ввода:
     - **RU-ввод:** промпт = введённое слово; ответ = перевод выбранного смысла.
     - **EN-ввод:** ответ = введённое слово; промпт = русский перевод смысла.
3. **Фоллбэк для редких слов** (нет в словаре даже с MORPHO): LLM одним вызовом
   отдаёт перевод + пример; при добавлении показываем пометку **«Переведено с
   помощью LLM, проверь»** — только ДО сохранения: «Сохранить» и есть
   подтверждение, итоговая ✅-карточка остаётся в чате уже без неё. Дальше слово
   обычное (повторяется наравне со всеми).
   Пометка «fallback» — флоу-онли маркер (нудж проверить догадку LLM ДО сохранения);
   провенанс намеренно не хранится в БД (после сохранения карточка уже подтверждена
   юзером, а пост-сейв это поле никто не читал — см. §11).
4. **Пример через LLM:** кормим LLM выбранным переводом, получаем одно русское
   предложение со словом + его английский перевод (всегда формат RU→EN).
5. **Ответ-подтверждение** показывает карточку (слово → перевод, пример) с
   действиями: **«Другой пример»** (перегенерировать пример), **«Свой перевод»**
   (переопределить перевод своим — для ЛЮБОЙ карточки: словарной, фоллбэк или уже
   переопределённой; вводишь свой вариант → пример перегенерируется под него, а
   пометка «проверь» снимается) и **«Свой пример»** (своё русское предложение-
   контекст; английская половина — КОНСТРЕЙНД-перевод LLM, обязанный использовать
   `english` карточки: свободный MT мог бы перефразировать само учимое слово —
   ровно это делает Яндекс.Переводчик с редкими словами. Перевод заданного текста —
   констрейнд-задача, в отличие от свободной генерации примера, где LLM без
   контекста может промахнуться). Словарный перевод авторитетен по умолчанию, но
   при желании переопределяется явной кнопкой; омограф закрыт выбором смысла
   (шаг 2), полноценная правка карточки — в §10. Дубль по русскому промпту
   помечается («возможно, уже есть: …»).
6. Сохранение в БД, `next_review = завтра`. То же сообщение редактируется в
   сохранённую карточку с **✅ перед словом** (без отдельной строки «Сохранено»/id,
   без кнопок — это и есть сигнал «сохранено»; to-do §UX).

**Концептуально:** каждый перевод Yandex (`tr`) — отдельный выбор-карточка
(замок: castle / lock; и даже дом: house / home — Yandex отдаёт их разными `tr`).
Синонимы (`tr.syn`) в ответ не идут — карточка = один перевод. Принимать несколько
вариантов = ручная правка карточки позже (§10).

## 5. Флоу: повторение (активный ввод)

**Запуск.** По расписанию планировщик во `review_time` шлёт «🔔 Регулярное повторение:
N слов» с кнопкой **«Начать»** (тап раскрывает первую карточку в ТОМ ЖЕ сообщении), ИЛИ
командой `/repeat` (тогда сегодняшнее плановое пропускается — идемпотентность по
`users.last_reviewed_on`). **Ручной и плановый запуск идентичны** (всегда N слов); кнопка
отличается лишь тем, что переиспользует сообщение-напоминание. Кнопка (а не сразу карточка)
— намеренно: тап идёт через обычный middleware и получает настоящую сессию, планировщику не
нужно инъектировать состояние извне.

**Планировщик шлёт ежедневно, пока колода непуста** (модель «всегда N» — дней отдыха нет).
Молчит только при пустой колоде.

### Отбор слов: всегда N (новые + самые созрелые)
Сессия — всегда `N = min(session_size, размер колоды)` слов. Состав (`selectSession` + чистый
`composeSession`):
1. **Новые слова** (`last_tested IS NULL`) — старейшие первыми (FIFO по `created_at`), **не
   больше `new_per_day`** за сессию. Куча новых истощается по мере ввода; гнать новые быстрее
   нельзя — защита от перегруза/интерференции.
2. **Остаток N добивается изученными** (`last_tested IS NOT NULL`) с **наименьшим `next_review`**
   (самые «созрелые» первыми). **Due-гейта нет** — берём самые созрелые независимо от того,
   наступил срок или нет; кончились новые → их место занимают изученные → всегда N.

Дискриминатор «новое vs изученное» — `last_tested` (NULL = ни разу не было в сессии): новое и
проваленное-сегодня по `next_review`/`interval_index` неразличимы. Порядок в сессии: изученные
(разминка) сначала, новые в конце.

**Трейд-офф «всегда N» (выбрано осознанно).** Без due-гейта иногда повторяем ещё-не-созрелое
(мягкий over-review — ок для ежедневной привычки); и каждый верный ответ двигает слово по
лестнице, поэтому гонять `/repeat` по кругу на маленькой колоде = интервалы быстро раздуются.
Принято ради «всегда есть что повторять» (для личного бота с маленькой колодой это важнее
SRS-пуризма). Альтернатива «двигать расписание только первый прогон за день» — отложена.

**Сигнал «не успеваешь».** Даже при «всегда N» очередь просроченных может расти, если слов
созревает больше, чем N/день успевает закрывать (большая колода / быстрый темп добавления).
Планировщик считает `backlog` (просроченных, `next_review <= today`) с гистерезисом: держится
выше N ≥3 дня подряд И куча новых непуста → в напоминание дописывается «очередь растёт, замедли
добавление или подними N до M» (`updatePaceCounters`; счётчики `backlog_strikes`/`ahead_strikes`
на `users`). Парный сигнал «успеваешь — добавь ещё» пока только копится (доставка отложена).

### Сессия — ОДНО редактируемое сообщение
**Активное извлечение:** показываем русское слово + русский пример как подсказку (английского
нет — не палим ответ), **ждём печатный английский**. Одна кнопка — **«Показать ответ»**.
```
1/5

дом
Мой дом большой.

Напиши перевод на английский:
```
Ввод юзера удаляется (в чате только флоу-сообщение). Грейдинг детерминированный (§6).
Результат предыдущей карточки и СЛЕДУЮЩИЙ вопрос — в одном сообщении, **авто-переход без
«Дальше»** (правильный ответ виден над следующим вопросом, пока отвечаешь):
- **Верно** → ✅ + полная карточка (RU/EN слово + RU/EN пример). `interval_index` растёт по
  лестнице (§7) — именно правильный ВВОД двигает SRS (старый «тест» верный ответ не двигал).
- **Неверно** → ❌ + правильная карточка; `interval_index` сброшен, `lapses++` (раз за
  сессию), слово уходит в КОНЕЦ цикла на пересдачу.
- **«Показать ответ»** → правильная карточка; засчитывается как провал, но из цикла слово
  уходит (не пересдаётся) — аварийный выход.
```
✅ Верно! «дом» — «house»
Мой дом большой.
My house is big.

— — —

2/5

кот
…
Напиши перевод на английский:
```
Счётчик — `закрываемая/всего`, **1-based**: первая `1/N`, последняя `N/N`. Номер — это
ЗАКРЫВАЕМАЯ карточка (`закрыто + 1`); на пересдаче честно повторяется (карточка всё ещё
закрывается), за `N` не выходит по построению. (Изначально был 0-based — `0/3` читался как
баг, и `N/N` не показывался.)

### Цикл, конец, коллизии
Неправильные/раскрытые слова возвращаются в конец очереди, пока на все не дан верный ответ.
**Сессия кончается с пустой очередью** → сообщение правится в **итог** (счёт + список слов с
ошибками) и остаётся в чате (это результат, §UX). Выборка **снапшотится на старте** (грейдинг
меняет `next_review`/`last_tested`, что иначе переупорядочило бы перезапрос); цикл — FIFO по
id, поэтому линейного «seen»-исключения больше нет. Любой НЕ-текст в REVIEW — шум, удаляется.
Пустой/русский ввод не грейдим (иначе сбросил бы SRS) — переспрашиваем ⚠️. **Таймаут 20 мин**
с последней активности → сессия закрывается на следующем касании (недоотвеченные слова не
затронуты).

## 6. Грейдинг ответа

Проверка печатного ответа — **детерминированная, без LLM** (крутится без присмотра,
ошибка молчаливая и вредная — §3). Реализация — `lib/grading.ts` (`isCorrect`/
`normalizeAnswer`) + `lib/lang.ts` (детект кириллицы):
- нормализация: lowercase, trim, схлопнуть пробелы, срезать ведущий артикль (a/an/the),
  срезать ведущее «to» у глаголов;
- верно = нормализованный ввод совпадает с `english` карточки;
- синоним (не сам ответ) → неверно; опечатка → неверно; пропущенный артикль/`to` → прощаем;
- пустой/пробельный ввод и кириллицу **НЕ грейдим** (это не провал — иначе сбросило бы SRS):
  переспрашиваем на той же карточке ⚠️-пометкой.

Последствия для расписания (promote / reset / `lapses`) — §7; учебный цикл (показываем
правильный ответ, ошибки пересдаются) — §5.

## 7. Расписание / SRS

- У каждого слова: `next_review` (дата), `interval_index` (позиция на лестнице),
  `lapses` (счётчик провалов — для будущей ловли «личей»), `last_tested` (`timestamptz`;
  NULL = ни разу не было в сессии — дискриминатор «новое vs повторяемое», §5).
- Новое слово → `next_review = завтра`, `interval_index = 0`, `last_tested = NULL`.
- **Верный ответ** (печатный) → `interval_index++` (promote по лестнице),
  `next_review = сегодня + ladder[interval_index]`, штампуем `last_tested`. Ключевое
  отличие от старого «теста», который верный ответ НЕ продвигал по лестнице.
- **Неверный ответ / «Показать ответ»** → `interval_index = 0` (reset), `next_review =
  завтра`, штампуем `last_tested`, `lapses++` (раз за сессию). В сессии слово ещё
  пересдаётся (цикл §5); снапшот индекса синхронизируется с БД, чтобы поздняя пересдача
  считала promote/reset от ТЕКУЩЕГО индекса, а не от стартового.
- **`next_review` — это приоритет, а не «допуск».** Чем меньше — тем «созрелее». Выборка
  всегда берёт N: новые (≤ `new_per_day`) + изученные с наименьшим `next_review`, БЕЗ
  due-гейта (§5). `next_review` в прошлом — норма (слово давно ждёт), спец-обработки нет.
- Новый `next_review` всегда считается **от сегодня** (`сегодня + ladder[...]`), не от
  старой даты — просрочка не накапливается (пропустил неделю — слово не «улетает» дальше).
- Гранулярность — дата в TZ юзера; тай-брейк среди одной даты — `created_at`. Даты —
  строки `YYYY-MM-DD` (под колонку `date`), арифметика календарная: `todayInTz` + `addDays`
  в UTC, без JS-`Date` в локальной зоне сервера (`src/lib/dates.ts`).
- **Лестница** — конфигурируемый массив дней, дефолт `[1, 3, 7, 14, 30, 60, 120, 240]`
  (Anki-тип, ~×2 с затуханием); подкрутим на реальных данных.
- «Выученные» = высокий `interval_index`: большие интервалы, но слово **никогда не уходит
  из ротации навсегда** — возвращается по `next_review` (убирать выученное из повторения
  роняет удержание ~до 33%, Karpicke & Roediger 2008). Отдельного «архива»/теста нет.
- **Планировщик:** раз в минуту дешёвый гейт (время + идемпотентность по `last_reviewed_on`);
  раз в день шлёт, пока колода непуста (модель «всегда N», §5), дописывая сигнал «не
  успеваешь». Самолечение: тест `now >= review_time` (не `==`), пропущенная минута догоняется
  следующим тиком.

## 8. Состояния и коллизии (на пользователя)

FSM: **IDLE/добавление → REVIEW**. (Тест-режима больше нет — повторение и тест слиты
в один активный флоу.)

- Добавление работает только в IDLE; в REVIEW текст — это печатный ответ. Предикат
  `freeTextIn(mode)` (`src/context.ts`) фильтрует текстовые хендлеры по `session.mode` и
  **исключает команды**, поэтому `/`-команда не перехватывается обработчиком чужого режима.
- `/repeat` во время живой сессии → «Повторение уже идёт» (не перезапускаем); истёкшую/
  рассинхронную сессию сбрасываем и стартуем заново. Запуск повторения помечает
  «сегодняшнее плановое» как сделанное (идемпотентность по `last_reviewed_on`).
- Русский/пустой ввод в повторении → не грейдим, переспрашиваем «только на английском» (§6).
- Любой не-текст в REVIEW удаляется (в чате остаётся только флоу-сообщение).
- Таймаут сессии — 20 мин (ленивый, на следующем касании).

## 9. Настройки и меню

**Настройки:**
1. **Слов в день** на повторение (`session_size`, потолок = размер колоды).
2. **Новых слов в день** (`new_per_day`, диапазон `[1, 20]`).
3. Время ежедневного повторения.

**Реализация:** меню — **одно редактируемое сообщение, чисто кнопочное и БЕЗ
состояния** (в отличие от повторения, оно не держит сессию): каждый экран (главный /
редактор счётчика / выбор часа) — чистая функция от строки `settings` + размера колоды;
под-экран в callback-данных (`set:*`), id сообщения из самого callback'а. Поэтому новый
режим в FSM не нужен, и панель переживает рестарт (терять в памяти нечего).

- **Слов в день** — степпер `±1/±5`; на экране ЭФФЕКТИВНОЕ `reviewSessionSize(session_size,
  deck)` = потолок по колоде (§7), так что меню не расходится с реальной сессией. Шаг от
  эффективного — no-op на потолке не перезаписывает хранимое (дефолт переживает рост колоды).
- **Новых в день** — степпер `±1/±5` в диапазоне `[1, 20]`; минимум **1** (новые не
  паузятся — место кончившихся новых занимают изученные); привязки к колоде нет.
- **Время** — выбор только ЧАСА (сетка 6×4, 00–23); минуты пришпилены к `:00`. Планировщик
  технически поддержал бы минуты — гранулярность это решение UI.
- Валидация (потолки, мин) — клэмпинг в чистом `lib/settings`, значение валидно по
  построению. `timezone` из меню НЕ правится (env-seeded, см. ниже).

> Таймзона владельца пока через env `OWNER_TZ` (single-user, временно), сеется в
> `settings.timezone` при провижининге. Правильный путь — 4-й пункт с выбором TZ из меню
> (`known_issues.md` №6).

**Меню команд** (через `setMyCommands`):
- Повторение (`/repeat`)
- Настройки (`/settings`)

## 10. Жизненный цикл слова

- **Правка** перевода/сета и **удаление** слова. Эта же правка — механизм
  бэкстопов, которые мы заложили: (1) починить неверный перевод/пример от словаря
  или LLM (в т.ч. фоллбэк-слова); (2) убрать лишний смысл из сета ответов (кейс
  омографа «замок» — оставить только нужное значение). Отдельных фич под бэкстопы
  нет — всё делает один флоу редактирования слова.
- **«Выпуск» — не отдельная фича и не финал:** большие интервалы просто реже показывают
  слово, но оно остаётся в ротации (возвращается по `next_review`). Отдельного архива нет.

## 11. Схема БД

- `users` (id, tg_chat_id, created_at, last_reviewed_on `date`, backlog_strikes `int`,
  ahead_strikes `int` — гистерезис сигнала «не успеваешь», §5)
- `settings` (user_id, session_size, new_per_day, review_time, timezone)
- `words` (id, user_id, russian `text`, english `text` — один ответ,
  example_ru, example_en, next_review `date`, interval_index `int`, lapses `int`,
  last_tested `timestamptz`, created_at). Провенанс перевода (fallback/словарь) —
  флоу-онли маркер на добавлении (нудж «проверь»), в БД НЕ хранится: после сохранения
  карточка подтверждена юзером, а пост-сейв поле никто не читал.
- состояние сессий — grammY `session`, **только транзитивное состояние флоу**
  (`mode`, очередь карточек), in-memory: сбрасывается на рестарте — это желаемое
  поведение. Персистентные данные — только в таблицах выше.

Все таблицы с данными — с `user_id`, все запросы фильтруют по нему.
